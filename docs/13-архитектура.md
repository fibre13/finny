# Функциональная и компонентная архитектура

Документ выполняет пункт 5.3 технического задания. Серверной части нет (ТЗ 3.2): приложение работает полностью на устройстве, поэтому схема развёртывания и спецификация OpenAPI не требуются.

## 1. Функциональная архитектура

Приложение состоит из игрового цикла сезона и вспомогательных разделов. Сезон — три игровых дня: в начале сезона приходят 50 монет, ребёнок раскладывает их по трём банкам, в каждом дне решает три события и закрывает день, после третьего дня видит итоги сезона. Двор — главный экран; разделы открываются предметами на лугу и значками в шапке.

| Функция | Что делает ребёнок или взрослый | Экран | Правила |
|---|---|---|---|
| Знакомство и профиль | Открывает подарок, выбирает вид, окрас и украшения, придумывает игровое имя и уровень заданий | `GiftScreen`, `PetSetupScreen` | `NameFilter`, `Difficulty` |
| Двор | Видит «День N из 3», имя, баланс, самочувствие питомца и предметы-разделы; решает три события дня; после событий играет с питомцем («Поиграть») и закрывает день («Уложить спать»); видит подсказку и напоминания | `YardScreen`, `EventDialog`, `SavingsAskDialog`, `SurpriseDialog`, `MissedDialog` | `YardGuide`, `Season.pickDay`, `GameViewModel.answerEvent`, `GameViewModel.finishPeriod`, `PetSpeech`, `PetVoice` |
| План бюджета | Раскладывает все свободные монеты по банкам «Нужное», «Хочу» и «Копим на мечту»; после утверждения видит «План и факт сезона» и «Сейчас в банках», поправляет план («Изменить план») | `PlanScreen` | `GameViewModel.confirmPlan`, `SeasonExtras` |
| Покупки | Покупает нужное и желаемое, видит цену, направление, пользу и остаток в банках; при нехватке в банках на нужное — окно «Взять из копилки?» | `ShopScreen`, `SavingsAskDialog` | `Season.payment`, `GameState.buy`, `Season.visibleItems` |
| Копилка и цель | Выбирает мечту, видит срок, переходит к пополнению в плане («Изменить →»), забирает монеты на покупки с подтверждением, получает накопленную цель | `SavingsScreen` | `Savings`, `SavingsState.forecast` |
| Задания | Решает задания четырёх типов, получает объяснение; каждые три решённых задания открывают сюрприз в лавке, «Помоги своему питомцу» приносит монеты | `TasksScreen`, `TaskDetailScreen`, `SurpriseDialog` | `TaskChecking`, `TaskQueue`, `TaskVariation`, `Season.pendingSurprise` |
| Итоги сезона | После третьего дня видит план и факт по банкам, остаток и накопленное за сезон, переводит остаток в копилку, играет с питомцем и укладывает его спать | `SeasonResultScreen` | `Season.borrowNotes`, `GameViewModel.transferLeftover`, `GameViewModel.closeSeason` |
| Праздник роста | Видит рост питомца в трёх сценах | `GrowthCelebrationScreen` | `Growth` |
| Гардероб | Меняет окрас и надевает купленные украшения | `WardrobeScreen` | `Accessories` |
| Мой прогресс | Смотрит цепочку стадий, прожитые дни и сезоны, условия роста (мечты и задания), цель, число решённых заданий и сколько осталось до сюрприза, полученные цели | `HistoryScreen` | `Growth`, `Season.tasksToNextSurprise` |
| Словарик | Читает 13 финансовых терминов; «Скидка» и «Долг» — на уровне «Посложнее» | `GlossaryScreen` | `GlossaryTerms` |
| Как играть | Перечитывает цель игры и три решения | `OnboardingScreen` | — |
| Раздел для взрослого | Проходит барьер, видит, чему учит игра, прогресс, настраивает экранное время и движения, включает демонстрационный режим, сбрасывает профиль | `AdultScreen` | `ScreenTime`, `GameViewModel.resetProfile` |

Последовательность экранов повторяет сквозной сценарий Приложения А ТЗ: подарок → питомец и имя → двор с окном «Пришли монеты» → цель → план сезона → события дня → покупки → задание → «Уложить спать» → новый день; после третьего дня — итоги сезона → новый сезон.

## 2. Модули

Проект разделён на четыре модуля Gradle. Правила экономики не зависят от Android и проверяются модульными тестами на JVM.

```
                ┌──────────────────────────────┐
                │ app                          │
                │ экраны Compose, навигация,   │
                │ GameViewModel, AppState,     │
                │ правила сезона               │
                └──────┬───────────┬───────────┘
                       │           │
          ┌────────────▼───┐   ┌───▼────────────┐
          │ content        │   │ data           │
          │ JSON-контент,  │   │ Room: сущности,│
          │ проверка       │   │ DAO, переходы  │
          │ ответов, имя,  │   │ схемы, запись  │
          │ графика        │   │ и чтение игры  │
          └────────┬───────┘   └───────┬────────┘
                   │                   │
                ┌──▼───────────────────▼──┐
                │ core-economy            │
                │ чистый Kotlin: баланс,  │
                │ план, покупки, копилка, │
                │ питомец, день, доход    │
                └─────────────────────────┘
```

Зависимости (из `build.gradle.kts` модулей): `app` → `core-economy`, `content`, `data`; `content` → `core-economy` (`api`); `data` → `core-economy` (`api`). Обратных зависимостей нет.

## 3. Компоненты модулей

### core-economy — правила экономики

| Файл | Ответственность |
|---|---|
| `Money.kt` | Тип `Coins`: целые монеты без отрицательного баланса |
| `Budget.kt` | Направления `BudgetCategory` («Нужное», «Хочу», «Копим на мечту»), план дня и проверка суммы |
| `Shop.kt` | Позиции каталога, направление покупки, влияние на показатель |
| `Savings.kt` | Цель, копилка, взнос и снятие, срок достижения по средним взносам за последние 9 периодов |
| `Pet.kt` | Показатели «Забота» и «Радость», уровни, стадии развития, снижение за день |
| `Period.kt` | Итог дня: условия дня, расходы по направлениям, пополнение копилки, неудачный день |
| `Income.kt` | Источники дохода и суммы: стартовый бюджет, монеты сезона, подарок, награда за помощь питомцу; объявлены также карманные монеты и награды за обычные задания, по которым приложение не начисляет |
| `Difficulty.kt` | Уровень заданий «Попроще» или «Посложнее» |
| `GameState.kt` | Неизменяемое состояние игры и переходы: план, покупка, взнос, снятие, завершение дня (в том числе без плана дня, `force = true`), новый день |

Каждое действие — чистая функция: принимает состояние и возвращает новое состояние с событием или отказом с причиной. Благодаря этому одни и те же правила проверяются тестами и исполняются приложением.

## 4. Поток данных

```
 экран ──действие──▶ GameViewModel ──▶ GameState (core-economy) ──▶ новое состояние
   ▲                      │                                            │
   │                      └──── Explanations: текст отклика ◀──────────┤
   │                                                                   ▼
   └──────────── StateFlow<AppState> ◀──────────────────────── AppState
                          │
                          └──▶ автосохранение: GameRepository.save (Room, одна транзакция)
```

1. Экран вызывает метод модели: например, `buy("food")`.
2. Модель применяет правило `GameState.buy`. Результат — новое состояние и событие или отказ с причиной (например, нехватка монет).
3. `Explanations` формирует сообщение: что изменилось, почему и что делать дальше.
4. Новое `AppState` публикуется через `StateFlow`; экраны перерисовываются.
5. Каждое изменение состояния записывается в базу (`GameViewModel`, блок автосохранения): прогресс переживает закрытие приложения (ТЗ 2.5.13). Состояние сезона `AppState.extras` записывается в поле `profile.extras` строкой JSON (`SeasonExtras.encode`).
6. При запуске модель читает сохранённую игру (`GameRepository.load`) и восстанавливает состояние сезона (`SavedGame.toAppState`, `SeasonExtras.decode`). Если строка `extras` пустая (профиль, сохранённый до версии базы 10), номер сезона определяется по текущему игровому дню, а достигнутая стадия считается отпразднованной. Если профиля нет, открывается знакомство.

Решения сезона проходят тот же путь с дополнительными шагами в `GameViewModel`:

| Действие | Шаги |
|---|---|
| Вход в приложение (`onSessionStart`) | `startNewDayIfDue`: `expireSeasonIfDue` закрывает сезон, не законченный за 6 календарных дней; `beginDay` начинает новый день: внутри сезона монеты не начисляются, в обычном режиме выводится сообщение «Новый день! День N из 3 в сезоне.», в начале сезона начисляются 50 монет (`GameState.earn`, `IncomeSource.SEASON_MONEY`), создаётся новое `SeasonExtras` и выводится окно «Пришли монеты»; `ensureDayEvents` выбирает три события дня (`Season.pickDay`) |
| Утверждение плана (`confirmPlan`) | Проверка, что разложены все монеты; взнос в копилку `GameState.deposit`; банки и план сезона записываются в `SeasonExtras`; затем `ensureDayEvents` |
| Покупка (`buy`) или затратное событие (`answerEvent`) | `Season.payment` определяет источники монет; при нехватке банков на нужное — запрос `savingsAsk` и окно «Взять из копилки?»; после подтверждения `GameState.withdraw` и `GameState.buy`; банки и факт сезона уменьшаются по источникам |
| Незатратное событие | Изменение показателя питомца; подарок — `GameState.earn` с источником `IncomeSource.GIFT` |
| Итог события (`finishEvent`, `closeEventResult`) | Эмоция и подсказка в `eventResult`; при отказе от желаемого — предложение перевести его цену в копилку (`GameState.deposit`) |
| Ответ на задание (`answerTask`) | Проверка ответа; монеты только за «Помоги своему питомцу»; счётчик решённых заданий, сюрприз `Season.pendingSurprise`; стадия `withGrowth` |
| «Уложить спать» (`finishPeriod`) | `GameState.finishPeriod(payIncome = false, force = true)`; после третьего дня — признак `seasonDone`, двор открывает `SeasonResultScreen` |
| Итоги сезона | `transferLeftover` переводит остаток банков и свободных монет в копилку; `closeSeason` начинает новый сезон сразу в демонстрационном режиме или если итоги закрыты в следующие календарные сутки, иначе — при первом входе в новые сутки |

Учебный контент читается из `assets` один раз на процесс и в базу не записывается: новое задание добавляется записью в `tasks.json`, новое событие дня — записью в `events.json` без изменения кода (ТЗ 2.5.14).

## 5. Схема обновления учебного контента

1. Задание, товар, цель, событие дня или термин добавляется записью в соответствующий JSON в `content/src/main/assets/`. Поля задания описаны в docs/01, раздел 7. У события дня задаются вид (`cost`, `mandatory`, `group`), цена и банк (`price`, `category`), влияние при согласии и отказе (`stat`, `stat_delta`, `decline_stat`, `decline_delta`), подсказки и эмоции, условия появления (`requires_scenery`, `requires_no_scenery`, `requires_goal`, `follows`). Товар-сюрприз — запись в `shop.json` с порогом `unlock_after`; термин только для уровня «Посложнее» — запись в `glossary.json` с признаком `hard_only`.
2. Картинка к заданию или значок события — существующий спрайт или новый исходник в `art/pixel/src/` со сборкой `art/pixel/tools/build.py`.
3. Автотесты `TaskContentTest`, `TaskQueueTest`, `TaskVariationTest`, `ContentFilesTest` проверяют полноту полей, темы на каждом уровне, пределы чисел для уровня «Попроще» и связность переменных чисел; `SeasonTest` читает `events.json` и `shop.json` и проверяет состав дня (обязательное, затратное и незатратное события), продолжение отказа и открытие сюрприза.
4. Новая сборка приложения доставляет контент пользователю через магазин приложений. Серверной доставки контента в прототипе нет.
